# 기술 구성과 개발 방법

## 제안하는 개발 구성

| 영역 | 선택 | 역할 |
| --- | --- | --- |
| 게임 클라이언트 | TypeScript + Three.js | 쿼터뷰·캐릭터·맵·애니메이션·시각 효과 |
| 일반 UI | React + CSS | 가방·제작·거래·채팅·설정 |
| 개발·빌드 | Vite | 브라우저 개발 서버·정적 배포물 |
| 서버 | C# + .NET 10 LTS + ASP.NET Core | 인증·게임 규칙·맵·보상·생산·거래 |
| 실시간 통신 | 초기 SignalR, WebSocket 전송 우선 | 이동 의도·주변 상태·전투 이벤트·채팅 |
| 영구 저장 | PostgreSQL 18 계열 | 계정·아이템·작업·건물·거래 |
| 배포 | Linux + 역방향 프록시 + 정적 자산 저장소 | HTTPS·WSS·압축·캐시·서비스 실행 |
| 3D 제작 | Blender + GLB/glTF 2.0 | 모델 정리·리깅·애니메이션·배치 자산 |
| 개발 검증 | 클라이언트 단위 검사·서버 통합 검사·브라우저 자동 확인 | 규칙·경제 원자성·실제 플레이 |

현재는 선택안이며 의존성 설치·프로젝트 생성은 하지 않았다. .NET 10은 현재 LTS 공식 정책을 확인해 선택했다. Three.js는 WebGL2 경로와 glTF 로더를 제공한다. Vite·Three.js·React의 정확한 패키지 버전은 실제 프로젝트 시작일에 호환 조합을 확인해 잠금 파일로 고정한다. Node 런타임도 그 Vite 버전의 공식 요구사항에 맞춰 고정한다.

## 선택 이유

기존 C# 서버 방향을 유지하면서 웹 화면만 별도로 구현한다. Three.js는 게임 엔진 전체가 아니므로 입력·맵 관리·전투 상태·UI 연결·자산 로딩은 직접 구성한다. 웹으로 이동하면 Unity 장면·컴포넌트를 그대로 재사용하는 것이 아니라 제작법·기획·권리 확인된 자산을 옮기는 것이다.

상시 30명·실시간 전투에서는 클라이언트가 아이템·피해·좌표 결과를 결정하면 안 된다. 브라우저는 입력과 예측 표현을 담당하고 서버가 이동 가능 범위·공격 범위·스태미나·재료·작업·보상을 확정한다.

## 첫 서버 구조

처음에는 하나의 .NET 애플리케이션 안에 API와 맵 시뮬레이션을 기능별로 분리한다. Auth, World, Combat, Harvest, Inventory, Production, Housing, Market, Social, Admin 경계를 둔다. 채널과 활성 지역은 별도의 상태 소유자를 갖고, 각 지역의 명령은 순서대로 처리한다.

게임 틱 목표는 20Hz, 주변 상태 전송은 10Hz부터 시험한다. 전체 월드가 아니라 주변 관심 영역의 변경만 전송한다. 클라이언트는 약 100ms 보간 창부터 시험하고 자신의 이동만 제한적으로 예측한다. 공격은 클라이언트 입력 시각을 무조건 신뢰하지 않고 허용 시간 창·사거리·속도·공격 상태를 검증한다. 정밀 지연 보정은 초기 이동·전투 검증 뒤 결정한다.

SignalR는 연결과 그룹 전송을 돕지만 게임 루프를 대신하지 않는다. 30명 밀집·인위 지연 시험에서 전송량·지연이 목표를 벗어나면 MessagePack·전송 주기·관심 영역을 먼저 측정하고, 필요하면 원시 WebSocket 프로토콜로 교체한다. 교체 여부를 구현 전 추측으로 확정하지 않는다.

Redis·메시지 브로커·여러 서비스 분리는 초기 필수가 아니다. 단일 프로세스 안에서 확장 지점을 유지하고 실제 병목 이후 도입한다. 지역 상태와 재산 소유권을 구분해 프로세스를 나눠도 중복 처리되지 않게 한다.

## 충돌과 이동

초기 지형은 높이 정보·보행 가능 영역·단순 충돌체를 사용한다. 서버도 같은 버전의 단순 충돌 데이터를 읽는다. 몬스터는 구역 기반 경로와 제한된 추적을 사용한다. 시각 모델의 모든 삼각형을 서버 충돌에 사용하지 않는다.

복잡한 강체·차량·파괴 물리는 초기 범위에서 제외한다. 상호작용과 공격은 원·캡슐·부채꼴 같은 프록시로 시작하고 회전·높낮이·벽 관통 검사를 포함한다. 실제 물리 엔진 선택은 그런 콘텐츠가 필요해질 때 성능과 C# 서버 호환을 검증한다.

## 저장할 데이터

| 저장 단위 | 주요 내용 |
| --- | --- |
| 계정·세션 | 계정 식별·권한·활성 캐릭터·토큰 수명 |
| 캐릭터 | 위치·지역·상태·장비·숙련·해금 |

| 생산 작업 | recipe_id·예약/실행/완료/수령·입출력 스냅샷·완료시각·content_version |
| 해체 권리 | encounter_id·캐릭터·집중 선택·보상 확정·수령 상태 |

정적 기획 JSON과 이용자의 현재 상태 DB는 다르다. 현재 JSON을 그대로 사용자 저장 파일로 사용하지 않는다. JSON에 적힌 수식 문자열은 설명이며 실행 가능한 스크립트로 평가하지 않는다.

## 요청과 저장의 일관성

공격은 입력 순번·무기 상태·대상 위치를 검증한다. 제작 시작은 재료 잠금/소비와 작업 생성, 작업 수령은 결과 지급과 수령 상태, 구매는 재화 차감과 소유 이전을 각각 원자적으로 확정한다. 동일 요청의 재시도는 동일 결과를 반환한다. 실패한 작업의 일부만 반영하지 않는다.

아이템과 화폐 조작은 DB 거래 및 고유 제약·동시성 검사를 사용한다. 전투 중 체력·AI 상태와 모든 이동 틱을 매번 DB에 기록하지 않는다. 지역 서버가 살아 있는 동안 메모리에서 관리하고 재산 변화·주기 저장·체크포인트 정책으로 나눈다.

## 브라우저와 자산 예산

PC 우선 목표 60fps·1080p, DPR 상한 1.5, 일반 장면 드로콜 200 안팎·삼각형 35만 안팎부터 시험한다. 이 숫자는 실제 품질과 기기 검증 전의 예산이다. 모바일 30fps는 후속 목표다. 큰 장식·화려한 후처리보다 공격 가독성과 안정적인 프레임을 우선한다.

모델은 GLB, 반복 나무·바위는 인스턴싱, 지역은 분할 로딩, 텍스처는 용도별 해상도·압축을 사용한다. 캐릭터·장비·몬스터의 본 수·애니메이션·재질을 제한하고 사용하지 않는 자원을 해제한다. 처음부터 모든 지역과 외형을 다운로드하지 않는다.

모델·아이콘·음향은 동일 아트 기준과 사용권을 확인한 자산 또는 생성 후 정리한 자산으로 준비한다. 이번 단계에서는 자산 생성·구매·API 호출을 하지 않았다. 자산 도구·예산·품질 게이트는 실제 제작 단계에서 결정한다.

## 개발 순서

1. 이 문서·정적 데이터의 지역·수치·제작 연결 검토.
2. 최소 브라우저 장면·이동·서버 연결과 2인 동기화.
3. 몬스터 1종·공격 예고·쓰러짐·개인 해체 권리.
4. 가죽 전처리·무두질·건조·가방까지의 생산 흐름.
5. 개인 거점·창고·건축·오프라인 작업·재접속.
6. 4인 협동과 지역 이동·소유권·복구 검증.
7. 습지·도기·약재·방수·농사 생활 알파.
8. 채널 10→20→30명·밀집 전투·거래 원자성 시험.
9. 운영·복구·차단·신고·백업·고정가 시장.
10. 협곡·냉대림·우림·상위 원정·공동 정착지를 순차 확장.

개발 일정은 첫 이동·전투·생산 구간의 실제 소요와 자산 제작량을 확인한 뒤 산정한다. 처음부터 전체 콘텐츠를 완성하는 일정으로 약속하지 않는다.
